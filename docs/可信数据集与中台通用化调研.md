# 可信数据集与中台通用化调研

> **调研主题**：①可信数据集的获取渠道与可信性方法论；②数据集在数据中台中的资产化管理；③数据中台从单项目走向通用化的关键方面与落地路线
> **调研日期**：2026-11-08（所有来源均于当日访问核实；仅快照级核实者以 ⚠️ 标注）
> **调研方式**：WebSearch / WebFetch 逐条核实官方文档、论文、官方博客。每个关键论断后以 [[N]](URL) 标注来源编号，文末「参考来源」列出全部 URL。
> **与本仓已有文档的分工**：《数据中台调研.md》已覆盖信通院六层架构 / OneData / 湖仓一体；《数据集资源清单_网络资料.md》已覆盖 26 个公开评测基准清单。**本文不重复上述内容**，定位为三者的补充：可信获取渠道、可信性方法论、元数据管理方案、通用化演进路线。

## 0. 摘要（TL;DR）

1. **可信数据集的"可信"来自机制而非口碑**：主流渠道分别用 DOI 版本化（Zenodo）、结构化元数据校验（HuggingFace dataset card YAML）、许可证标注（Kaggle/CC）、schema.org 标记入索引（Google Dataset Search）、引用元数据（UCI）来兜底；**渠道本身也有生命周期**——Papers with Code 已于 2025-07-24 关站并重定向到 HuggingFace，迁移过程还丢过数据集条目 [[39]](https://paperswithcode.com/datasets)。中台引用外部数据集时应把"上游渠道存活性"纳入风险登记。
2. **方法论层面有四张现成的"数据集身份证"**：Datasheets for Datasets（Gebru et al.，CACM 2021）[[8]](https://arxiv.org/abs/1803.09010)、Data Statements（Bender & Friedman，TACL 6）[[9]](https://aclanthology.org/Q18-1041/)、FAIR 15 原则 [[10]](https://www.gofair.foundation/fair-principles/)、MLCommons Croissant 元数据标准（2026 年 2 月已发布 1.1 版，70 万+ 数据集可经 Google Dataset Search 互操作发现）[[7]](https://mlcommons.org/working-groups/data/croissant/)。个人中台最低成本做法：YAML 数据集卡对齐 Datasheets 问题清单 + Croissant JSON-LD 描述文件。
3. **基准污染是评测中台的系统性风险**：综述 [[12]](https://arxiv.org/abs/2406.04244) 把污染分为语义/信息/数据/标签四级，检测分"匹配式"与"对比式"两大类（n-gram 重叠、成员推断、顺序似然、时间断面分析等），缓解靠动态基准与数据再生——VibeMemory 的自建评测集（pooled 协议、查询全池唯一）天然属于"策展新数据"路线，应把这条纪律写进数据集卡。
4. **元数据/数据目录四件套现状分化**：DataHub（元数据图 + Kafka 事件流，`datahub docker quickstart` 单机起）[[17]](https://github.com/datahub-project/datahub)、OpenMetadata（schema-first 元数据知识图谱，已原生支持 ODCS 3.1 数据契约）[[18]](https://github.com/open-metadata/OpenMetadata)、OpenLineage（血缘采集开放标准：run/job/dataset + facet）[[20]](https://github.com/OpenLineage/OpenLineage) 均活跃；**Amundsen 已于 2026-09-29 归档为只读**[[19]](https://github.com/amundsen-io/amundsen)，新选型不应再入。
5. **数据契约的行业标准已收敛到 ODCS**：datacontract.com 的 Data Contract Specification v1.2.1 已官方声明弃用、建议迁移到 Bitol（Linux Foundation）的 Open Data Contract Standard（当前 v3.2.0）[[24]](https://github.com/datacontract/datacontract-specification)、[[25]](https://github.com/bitol-io/open-data-contract-standard)。
6. **轻量中台的通用化不必上重型基建**：DuckDB 官方博客的「Modern Data Stack in a Box」（Meltano + DuckDB + dbt + Superset）给出方法论——"It sacrifices infinite scale for significant simplification"[[37]](https://duckdb.org/2022/10/12/modern-data-stack-in-a-box.html)；接入层用 Singer 式 tap/target 协议（RECORD/SCHEMA/STATE 三类消息）[[27]](https://github.com/singer-io/getting-started) 即可把现有 15 类来源"descriptor 化"，血缘先用 OpenLineage 事件落地 JSONL，表格式（Iceberg/Delta/Hudi）在出现多写者/时间旅行需求前可以不引 [[30]](https://iceberg.apache.org/docs/latest/)、[[31]](https://docs.delta.io/latest/index.html)、[[32]](https://hudi.apache.org/docs/overview/)。
7. **对本中台的落地路线**（详见第 4 章）：M0 固化（数据集卡补齐）→ M1 适配器化（sources.json → source descriptor + extractor）→ M2 元数据外化（Croissant + OpenLineage 事件）→ M3 版本契约化（revision 三元组 + ODCS 简版契约）。每一步都不引入服务器常驻新组件，兼容现有一台 instabox + autopull 的部署形态。

## 1. 如何获取可信数据集

**渠道选型结论（对个人/单人中台）**：

- **第一优先**：HuggingFace datasets——revisions 提供了免费、按 commit SHA 锚定的可复现性 [[16]](https://huggingface.co/docs/datasets/en/loading)，dataset card 的 YAML license 字段可被脚本直接解析入库，与本仓"SHA-256 指纹 + 数据集清单"的做法天然互补。
- **需要学术引用时**：Zenodo concept/version DOI 双层锚点 [[4]](https://zenodo.org/help/versioning) 最稳——论文里引 DOI，中台 manifest 里同时记 DOI 与本地 SHA-256。
- **国内镜像/加速**：OpenDataLab、ModelScope 可作下载通道，但**可信锚点仍应回指上游**（上游 GitHub/HF 的 commit + SHA-256），镜像渠道只当 CDN 用。
- **渠道风险**：PwC 关站事件说明"渠道域名"不是稳定标识，来源登记应存"渠道无关"的锚点（DOI/commit SHA/上游 URL）[[39]](https://paperswithcode.com/datasets)。

### 1.2 数据集可信性评估方法论：四张"数据集身份证" + 许可证 + 污染

**(a) Datasheets for Datasets（Gebru et al.）**。借鉴电子元器件规格书，主张每个数据集附带标准化说明书，覆盖动机、构成、采集过程、推荐用途等维度，发表于 CACM 2021 [[8]](https://arxiv.org/abs/1803.09010)。落地时最有用的是它的提问式清单——这些问题（采集自谁、如何采样、有无缺失、推荐/不推荐用途）正好可以做成中台数据集卡的必填项。

**(b) Data Statements for NLP（Bender & Friedman）**。TACL 第 6 卷（2018）提出为数据集写"数据声明"，缓解用某些人群数据为其他人群开发技术带来的系统偏差 [[9]](https://aclanthology.org/Q18-1041/)。对中文多方言/多领域语料尤其相关：数据集卡应至少声明语言/方言覆盖面与采集语境。

**(c) FAIR 原则**。Findable/Accessible/Interoperable/Reusable 共 15 条（F1–F4、A1/A1.1/A1.2/A2、I1–I3、R1/R1.1/R1.2/R1.3），核心可执行项：持久标识符（F1）、丰富元数据（F2）、开放协议（A1.1）、受控词表（I2）、明确许可（R1.1）、来源/沿袭信息（R1.2）、社区标准（R1.3）[[10]](https://www.gofair.foundation/fair-principles/)。注：原域名 go-fair.org 现已 301 重定向至 gofair.foundation。**本中台的 SHA-256 指纹 + 溯源档案实际上已经在做 R1.2**，补 F1/R1.1 即可对标。

**(d) MLCommons Croissant**。定位「an open, community-built, standardized metadata vocabulary for ML datasets」，基于 schema.org，用 FileObject/FileSet/RecordSet/Field 描述加载数据所需的一切；来源与权限描述基于 PROV-O 和 DUO 本体；配套 Python 库（mlcroissant）可校验与消费，TensorFlow/JAX/PyTorch 加载器已接入，HuggingFace/Kaggle/OpenML 的数据集均可通过 Google Dataset Search 以 Croissant 发现（70 万+）[[7]](https://mlcommons.org/working-groups/data/croissant/)。**2026 年 2 月已发布 Croissant 1.1**，并有 RAI/地理空间/生命科学领域扩展。这是"让外部工具读我的数据集"成本最低的一张身份证。

**(e) 数据许可证要点**。Creative Commons 六种组合 + CC0：所有组合强制署名（BY）；NC 定义为「not primarily intended for or directed towards commercial advantage or monetary compensation」；ND 禁止衍生改编；SA 要求改编作品同条款共享 [[11]](https://creativecommons.org/share-your-work/cclicenses/)。对本中台的三个实操提醒：

1. **允许商用与否决定资产可用范围**——本中台含公网大屏与未来多项目运营，引用 CC BY-NC 数据集（如 LoCoMo 的 CC BY-NC 4.0，已在《数据集资源清单》核实）的产出应标注"不可商用"或隔离到评测专用区；
2. Kaggle 侧受控许可值（cc/gpl/odb/other）与 HF 的 license 标识符两套词表并存，入库时应统一映射到中台自己的 license 字段 [[3]](https://github.com/Kaggle/kaggle-cli/blob/main/docs/datasets.md)、[[1]](https://huggingface.co/docs/hub/datasets-cards)；
3. CC 官方页面明确：AI 对内容的使用往往超出版权（因而超出 CC 许可证）所能规管范围，CC 正在开发 **CC Signals** 框架应对——LLM 训练用途目前属于"许可证未明确覆盖"的灰色区，引用数据用于训练时不应臆断许可 [[11]](https://creativecommons.org/share-your-work/cclicenses/)。

**(f) 基准污染（benchmark contamination）**。综述 [[12]](https://arxiv.org/abs/2406.04244)（含 HTML 全文 [[13]](https://arxiv.org/html/2406.04244v1)）给出体系：

- **定义与四级严重性**：LLM「inadvertently incorporate evaluation benchmark information from their training data」；按暴露程度分语义级（接触同话题/同源内容）→ 信息级（接触元数据/分布）→ 数据级（接触无标签数据）→ 标签级（接触完整基准），暴露越彻底、检测越难。
- **检测两大类**：匹配式（数据集检查：如 GPT-3 的 13-gram、GPT-4 的 50 字符重叠规则；成员推断；样例生成）与对比式（内容对比：相似度/困惑度；顺序分析：规范顺序 vs 打乱顺序似然差，可给出可证明保证；时间分析：按题目发布日期检测性能断崖）。综述同时批评 n-gram 法可被改述绕过（Evasive Augmentation Learning 场景下最高可白拿 15% 提升）。
- **缓解三路**：策展新数据（私有/动态基准，如 LiveCodeBench）、重构现有数据（数据再生、内容过滤）、benchmark-free 评测（LLM-judge、Chatbot Arena 式人工）。
- **对本中台的含义**：自建评测集（查询文本全池唯一、pooled 协议）属于"策展新数据"路线且自带抗污染属性；对外部基准（LoCoMo/LongMemEval 等）做评测结论时，应在数据集卡记录"上游版本 + 推理模型训练截止时间"以支撑时间断面分析 [[13]](https://arxiv.org/html/2406.04244v1)。

### 1.3 数据集版本化与可复现：三件工具 + 一个原生机制

| 工具 | 机制 | 关键能力 | 适用 |
|---|---|---|---|
| DVC | Git 仓库里存 `.dvc` 指针文件，数据实体进本地缓存，push/pull 同步到 remote（S3/OSS/GCS/GDrive/SSH/HDFS/HTTP 等） | `dvc add/commit/push/pull`、`dvc.yaml` 流水线、experiment tracking、Data Registry 场景官方点名 | 数据与代码同仓、想把"数据集某版本"和"代码某 commit"绑一起 [[14]](https://doc.dvc.org/) |
| lakeFS | 对象存储上的 Git 语义层：Repository/Branch/Commit/Merge/Revert/Tag/Hooks；建分支是零拷贝元数据操作，兼容 S3 API，格式无关（Delta/Iceberg 作为其集成项而非被替代） | 分支隔离、原子合并、回滚、**hooks 在 pre-merge 跑质量检查（WAP 写审计发布模式）**、与 MLflow 绑定实验到确切数据版本 | 已有对象存储、需要"数据 PR"协作或可复现实验 [[15]](https://docs.lakefs.io/) |
| HuggingFace revisions | 数据集仓库即 git 仓库 | `load_dataset(revision="commit-sha"/tag/branch)`，commit 历史在数据集页可见 | 引用外部 HF 数据集时零成本锚定版本 [[16]](https://huggingface.co/docs/datasets/en/loading) |
| （对照）Zenodo DOI | 出版级版本锚点 | concept DOI + version DOI | 对外引用与论文级溯源 [[4]](https://zenodo.org/help/versioning) |

**选型建议**：单人轻量中台不必立刻上 lakeFS（其价值在多人协作与对象存储规模化）；现有「git tag + SHA-256 manifest」做法与 DVC 的指针思想同构，DVC 可在数据体量增长后按需引入；对外部基准，**HF revision（commit SHA）+ Zenodo DOI（如有）双锚点**是最省力的可复现方案。

## 2. 数据集在数据中台中的应用

### 2.1 数据集即资产：目录、血缘、质量门禁、数据服务的业界做法

业界把"数据集当资产管理"落在四个能力上，开源方案已把标准形态打磨成熟：

- **资产目录（catalog）**：统一登记表/主题/指标/看板/管道/模型等资产，配 schema、统计画像、所有权、术语表。DataHub 自我定位为「The Context Platform for your Data and AI Stack」，列级血缘 + 自然语言搜索 + 质量断言是标配 [[17]](https://github.com/datahub-project/datahub)；OpenMetadata 把技术元数据、质量信号、血缘、所有权、策略、术语表、**数据契约与数据产品**整合进「a unified metadata knowledge graph」[[18]](https://github.com/open-metadata/OpenMetadata)。
- **血缘（lineage）**：表级 → 列级 → 管道级。OpenLineage 定义了「a generic model of run, job, and dataset entities」加 facet 扩展机制的开放标准，Spark/Airflow/dbt/Flink 等主流引擎都有官方集成，Marquez 是其参考实现后端 [[20]](https://github.com/OpenLineage/OpenLineage)。数据集型中台（区别于管道型）的血缘重点在"数据集 A → 加工 → 数据集 B"，与 OpenLineage 的 dataset 实体天然对齐。
- **质量门禁（quality gate）**：三种代表形态——断言式（Great Expectations：期望即「expressive and extensible unit tests for your data」，验证结果自动渲染 Data Docs）[[33]](https://github.com/great-expectations/great_expectations)；声明式（pandera：DataFrameSchema + Check，校验 pandas/polars/pyarrow/pyspark 等多后端，支持 lazy 聚合报错与假设检验）[[34]](https://pandera.readthedocs.io/en/stable/)；平台式（OpenMetadata 内置 tests/profiling/freshness/volume/null/uniqueness 检查与告警）[[18]](https://github.com/open-metadata/OpenMetadata)。**门禁的执行时机**可以借鉴 lakeFS hooks：在 pre-merge/pre-commit 事件上挂质量检查，低质量数据进不了主分支（Write-Audit-Publish 模式）[[15]](https://docs.lakefs.io/)。
- **数据服务 API**：DataHub/OpenMetadata 均提供 GraphQL/REST/SDK 对外暴露元数据与资产上下文 [[17]](https://github.com/datahub-project/datahub)、[[18]](https://github.com/open-metadata/OpenMetadata)；数据本身的"服务化"则由数据契约（见 2.4）与对象存储/查询引擎承担。信通院 OneService 口径的统一服务出口已在《数据中台调研.md》覆盖，此处不重复。

### 2.2 元数据管理/数据目录开源方案对比

| 维度 | DataHub | OpenMetadata | Amundsen | OpenLineage |
|---|---|---|---|---|
| 定位 | 数据与 AI 栈的上下文平台（元数据图） | 开放上下文层 / 数据目录 + 质量血缘治理 | 数据发现引擎（「Google search for data」） | 血缘元数据采集**开放标准**（非平台） |
| 架构 | GMS 元数据服务 + Kafka 事件流 + React 前端 + GraphQL；Python 摄取框架 150+ 集成 | schema-first 元数据知识图谱（700+ JSON Schemas）+ ingestion 服务 + UI；130+ connectors | frontend(Flask+React) / search(Elasticsearch) / metadata(Neo4j or Atlas) 三微服务 + databuilder 摄取库 | 规范（OpenAPI 定义）+ client SDK + 引擎集成；事件模型 run/job/dataset + facets |
| 元数据覆盖 | 表/列级血缘、画像、所有权、术语表、质量断言、新鲜度 SLA、AI 上下文（MCP） | 表/列级/仪表盘/管道/指标血缘、质量测试、术语表、域、**数据产品、数据契约（ODCS 3.1）**、MCP Server | 实体搜索与使用排序为主，血缘依赖 databuilder | 只管血缘（但与任何 catalog 可组合） |
| 最小可用形态 | `pip install acryl-datahub && datahub docker quickstart`（Docker 8GB 内存，localhost:9002）[[17]](https://github.com/datahub-project/datahub) | Docker 部署 + sandbox 在线试用 [[18]](https://github.com/open-metadata/OpenMetadata) | 需拉起三服务 + Neo4j/ES；**项目 2026-09-29 已归档只读** [[19]](https://github.com/amundsen-io/amundsen) | 无需常驻服务：事件直接 emit 到 JSONL/HTTP/Marquez [[20]](https://github.com/OpenLineage/OpenLineage) |
| 对单人轻量中台 | 偏重（Kafka+ES 常驻），适合资产量大后再上 | 偏重但功能最全；其 JSON Schema 模型可单独借鉴 | **不建议新采用**（已归档） | **最适合轻量起步**：先只采集事件，后端可先不建 |

**结论**：单人项目期，"自建资产目录 JSON + OpenLineage 事件"是最小可用形态；数据资产跨项目到几十上百个、且需要多人协作时，再评估 OpenMetadata（若想要质量+契约一体化）或 DataHub（若想要更强的摄取生态）。

### 2.3 AI/评测场景的数据集管理：配置 + 数据 + 指标三层

三个主流评测框架给出了同一抽象——**评测集是"配置引用数据、配置声明指标"的三层解耦**：

- **OpenCompass**（上海AI实验室，Apache-2.0）：模型与数据集各持一份 Python 配置（`configs/models/`、`configs/datasets/`），评测器可组合（`GenericLLMEvaluator` LLM 判分、`MATHVerifyEvaluator` 数学、`CascadeEvaluator` 串联），流水线四步「数据集和模型配置、推理、评测和结果总结」，100+ 数据集，外围有 CompassHub（基准导航）与 CompassRank（榜单）[[21]](https://github.com/open-compass/OpenCompass)。
- **lm-evaluation-harness**（EleutherAI，HF Open LLM Leaderboard 后端）：v0.4 起「Config-based task creation」——任务= YAML（数据集路径 + Jinja2 prompt 模板 + 输出后处理 + 指标 + fewshot 配置），提供 `templates/new_yaml_task` 与 new_task_guide，2026-09 新增插件机制（模型后端/过滤器/指标可从外部包注册，无需 fork），60+ 学术基准 [[23]](https://github.com/EleutherAI/lm-evaluation-harness)。
- **EvalScope**（ModelScope 社区）：CLI/Python `TaskConfig`/YAML-JSON 四种配置方式，`--datasets gsm8k arc --dataset-args {...}` 组织数据集，集成 OpenCompass/VLMEvalKit/RAGEval 多后端，特色在性能压测（TTFT/TPOT）、Arena 对战与 MCP/Agent 评测 [[22]](https://github.com/modelscope/evalscope)。

**对本中台评测层的启示**：评测中台的"评测集→运行→榜单"抽象与上述一致（《评测中台调研.md》已对齐 OpenCompass 式抽象）；数据集管理层应把"数据集"沉淀为**带版本锚点的独立资产**，评测配置只引用 `dataset_id@revision`，而不是把数据路径硬编码进用例——这正是 lm-eval YAML 与 OpenCompass config 共同示范的解耦。

### 2.4 Data contract 与 dataset-as-product（Data Mesh）

**Data contract（数据契约）**：

- 行业标准已收敛：datacontract.com 的 Data Contract Specification（YAML，对象含 info/servers/terms/models/definitions/servicelevels/quality/lineage）**已官方弃用**，声明转向「a single industry standard」——Bitol（Linux Foundation）的 **Open Data Contract Standard（ODCS）**，当前 v3.2.0 [[24]](https://github.com/datacontract/datacontract-specification)、[[25]](https://github.com/bitol-io/open-data-contract-standard)。
- 契约的核心价值是**把"质量"从下游检查前移到上游承诺**：quality 对象用 SQL 查询 + 阈值（mustBe/mustBeLessThan）声明机器可校验的质量条款，lineage 对象直接基于 OpenLineage 表达字段级血缘 [[24]](https://github.com/datacontract/datacontract-specification)。
- 平台侧落地信号：OpenMetadata 已原生支持 ODCS 3.1 数据契约资产 [[18]](https://github.com/open-metadata/OpenMetadata)。

**Data Mesh 与 dataset-as-product**：Zhamak Dehghani 的四原则——领域导向去中心化所有权、**数据即产品**（消费者即客户）、自助式数据基础设施平台、联邦式计算治理 [[26]](https://martinfowler.com/articles/data-mesh-principles.html)。数据产品是数据网格的架构量子：code（管道/访问控制）+ data & metadata（数据 + 语义/质量声明）+ infrastructure 三件一体，平台负责把治理规则自动化。**单人项目的取舍**：Data Mesh 的组织前提（多领域团队）不存在，但"data product = 数据 + 元数据 + 契约 + 质量指标打包交付"的产品化纪律完全可以单人多项目复用——这正是通用化的核心：**把每个项目的数据集当作给"下一个项目"消费的产品来做**。

## 3. 搭建通用数据中台的关键方面

### 3.1 多来源接入：适配器/连接器模式

业界把"接入新来源"收敛为**声明式 descriptor + 可插拔 extractor**，而不是每个来源写一段 bespoke 脚本：

- **Singer 规范**：抽取端叫 tap、加载端叫 target，两者以「a standard JSON-based data format over stdout」通信；tap 输出三类消息——RECORD（数据行）、SCHEMA（流结构）、STATE（增量游标/断点续传），另有 discovery mode 输出 catalog 供字段选择；任意 tap × 任意 target 可组合 [[27]](https://github.com/singer-io/getting-started)。
- **Airbyte**：700+ 连接器目录，低代码 Connector Builder UI + Python CDK；与 Airflow/Dagster/Kestra 编排器集成 [[28]](https://github.com/airbytehq/airbyte)。
- **Meltano**：把 Singer tap/target 作为一等公民做编排（`meltano run tap-xxx target-yyy` 一条语句跑通管道），DuckDB 官方「in a box」方案即以它为接入层 [[37]](https://duckdb.org/2022/10/12/modern-data-stack-in-a-box.html)。

**通用化的模式结论**：轻量中台不需要引入 Airbyte 这种常驻平台，但**值得抄它的接口形状**——source registry（来源登记表）+ 每来源一个 descriptor（凭据/路径/抽取器/指纹字段）+ extractor 统一输出（数据 + schema + 进度）。本中台现有 sources.json 已是 source registry 的雏形（见第 4 章）。

### 3.2 存储与格式选型：对象存储 / Parquet / 表格式

| 层 | 选项 | 关键事实 | 轻量中台取舍 |
|---|---|---|---|
| 文件格式 | **Parquet** | Apache 列式文件格式，规范含压缩/编码/Bloom Filter/加密/嵌套结构，ASF 项目 [[29]](https://parquet.apache.org/docs/) | **默认选它**：ODS 原始区可保留原始 JSON/CSV，DWD/DWS 统一 Parquet 化；DuckDB/HF datasets/PyIceberg 全都直读 |
| 表格式 | **Iceberg** | 「an open table format for huge analytic datasets」：可序列化隔离 ACID、schema/分区演进无副作用、隐藏分区、时间旅行「reproducible queries」、REST Catalog 协议；引擎支持 Spark/Trino/Flink/**DuckDB**/PyIceberg 等 [[30]](https://iceberg.apache.org/docs/latest/) | 需要 ACID 多写者、schema 演进、时间旅行时才引入；PyIceberg + DuckDB 是无 JVM 的轻量组合 |
| 表格式 | **Delta Lake** | 在数据湖之上建 Lakehouse：ACID、统一批流、schema 强制、时间旅行、MERGE/UPDATE/DELETE [[31]](https://docs.delta.io/latest/index.html) | 与 Spark 生态绑定最深；纯 Python 单机场景优势不明显 |
| 表格式 | **Hudi** | Uber 开创事务性数据湖；写优化 + 记录级索引（高效 upsert/delete）+ 增量查询一等公民；COW/MOR 两表型 [[32]](https://hudi.apache.org/docs/overview/) | 面向高频增量写入的管道；单人评测/实验型中台基本用不到 |
| 查询/计算 | **DuckDB** | 嵌入式 OLAP、进程内、单文件、向量化执行、零外部依赖；Parquet/JSON/HTTP(S)/S3 以扩展形式提供；MIT [[36]](https://duckdb.org/why_duckdb) | **轻量中台的查询层标配**：直接查 Parquet/JSONL，替代"为看板起数据库服务" |

**结论**：Parquet + DuckDB 是轻量中台的黄金组合（对象存储只在需要跨机共享/大文件归档时引入，MinIO/S3 兼容桶即可）；Iceberg 在出现"多进程并发写同一数据集 + 需要快照回溯"的真实需求前可以观望——这也符合 lakeFS 文档的定位：表格式与版本控制层是叠加关系而非互斥 [[15]](https://docs.lakefs.io/)。

### 3.3 数据质量规则引擎与数据安全/访问控制基础

**质量规则引擎**（与 2.1 质量门禁衔接）：

- 断言式：Great Expectations——期望即数据单元测试，验证结果自动渲染 Data Docs，Apache-2.0 [[33]](https://github.com/great-expectations/great_expectations)。
- 声明式：pandera——`pa.Column(int, pa.Check.ge(0))` + `schema.validate(df)`，支持多后端与假设检验，MIT [[34]](https://pandera.readthedocs.io/en/stable/)。单人 Python 中台推荐 pandera：规则即代码、随仓库版本化，与本中台"六性检查脚本化"的形态最接近。
- 平台式/事件式：OpenMetadata 内置质量测试与告警 [[18]](https://github.com/open-metadata/OpenMetadata)；lakeFS hooks 把质量检查挂到 pre-merge 事件形成 WAP 门禁 [[15]](https://docs.lakefs.io/)。

**数据安全与访问控制基础**（单人项目只需"够用的三件套"）：

1. **认证与授权分离**：MinIO 的模型可作参照——「policy-based access control」默认拒绝一切未显式授予的操作，认证可由内置/OIDC/LDAP 等提供，授权由策略引擎独立执行，策略语法兼容 AWS IAM 且 Deny 优先于 Allow [[35]](https://docs.min.io/enterprise/aistor-object-store/administration/iam/)。单人项目等价物：API token 分读写两把 + 目录权限。
2. **最小权限原则落到位**：只读消费者（大屏/评测运行器）永远拿只读凭据；写路径集中在流水线单一入口。
3. **审计与溯源即安全**：本中台已有的 SHA-256 指纹 + 变更检测档案，本质上是"数据完整性审计链"，是单人项目性价比最高的安全资产——比引入 IAM 系统更贴合实际威胁模型（数据被意外改写/覆盖）。

### 3.4 轻量/单人项目如何分阶段演进到通用数据中台

方法论样本：DuckDB 官方博客《Modern Data Stack in a Box》（2022-10）——Meltano（接入）+ DuckDB（存储计算）+ dbt（转换）+ Superset（BI），全笔记本可跑、全开源免费，管线一条语句执行；作者明确定价了取舍：「It sacrifices infinite scale for significant simplification」（用无限扩展性换显著简化），并指出可按数据主题复制多个"盒子"横向摊开 [[37]](https://duckdb.org/2022/10/12/modern-data-stack-in-a-box.html)。

从这套方法论 + 上文各节，可归纳出单人项目演进的四阶段骨架（结合本中台现状的逐条展开见第 4 章）：

- **M0 固化期**：不新增组件，把"隐式约定"显式化——数据集卡、来源 descriptor、license 字段。
- **M1 接口期**：把来源接入从"脚本集合"重构成"descriptor + extractor 接口"（Singer 形状）。
- **M2 元数据期**：输出机器可读元数据（Croissant JSON-LD、OpenLineage 事件），让外部工具/未来平台能自动理解资产。
- **M3 契约期**：对跨项目共享的数据集写简版 ODCS 契约（schema + quality 阈值 + terms），质量门禁从"定期体检"升级为"流水线阻断"。

每阶段的判停标准都应是"下一个新项目/新来源接入时，需要改动的既有文件数量是否下降"。

## 4. 对本数据中台的落地建议

### 4.1 现状盘点（承接《交接文档.md》《README.md》）

现有资产：**15 类来源**（仓库产物：实验文件/coverage.xml/STATUS/CHANGELOG/seed/tests/git/pyproject + 三中台回流：评测存档/评测集/基准数据集/测试存档/监控存档），15/15 在线；SHA-256 指纹 + 变更检测溯源；质量六性（GB/T 36344-2018 框架 + DAMA 有效维度）综合分 0.996；ODS/DWD/DWS 三层；13 资产目录（含血缘）；五张大屏；部署形态为 instabox 单机 + autopull 每 15 分钟轮询 GitHub。外部基准数据集已做过 SHA-256 与上游 results/*.json 的交叉验证。**已有的信通院/OneData 对标与 26 个基准清单见既有两份调研文档，此处不重复。**

对照第 1–3 章，差距集中在四处：(a) 来源接入仍是"脚本知道来源"而非"接口登记来源"；(b) 数据集卡不齐（license/用途/上游版本锚点未结构化）；(c) 版本锚点只有本地 SHA-256，缺上游 commit/DOI 外锚；(d) 资产元数据是人读的（大屏 HTML），缺机器读出口。

### 4.2 路线 M0–M3（不引入常驻新组件，全部兼容单机部署）

**M0：数据集卡补齐（1 天工作量，收益/成本比最高）**

- 为 15 类来源 + 全部外部基准各写一张 `dataset-card.yaml`，字段对齐 Datasheets 提问清单 [[8]](https://arxiv.org/abs/1803.09010) 与 HF dataset card 词表 [[1]](https://huggingface.co/docs/hub/datasets-cards)：`name / description / license / task_categories / size / source_url / upstream_revision（commit SHA 或 DOI）/ sha256 / 污染风险备注`。
- license 统一映射到一张中台内部许可词表（cc-by / cc-by-nc / proprietary / research-only …），NC 数据集打 `commercial_use: false` 标记——公网大屏展示与未来多项目运营前必须过这道检查 [[11]](https://creativecommons.org/share-your-work/cclicenses/)。
- 质量六性定义（GB/T 36344-2018 + DAMA）写进卡片元数据，作为 R1.3（社区标准符合性）的证据。

**M1：sources.json 适配器化（2–3 天）**

- 把现有 sources.json 升级为 Singer 形状的接口契约 [[27]](https://github.com/singer-io/getting-started)：每类来源一个 descriptor（`id / scheme / extractor / fingerprint: sha256 / outputs`），extractor 统一产出三类产物——`records`（数据）、`schema`（结构声明，可先省略）、`state`（增量/变更游标，对应现有变更检测）。
- 新项目接入 = 新增一个 descriptor + extractor 文件，流水线主体零改动；15 类来源的现有脚本逐步改写为 extractor 插件，一次迁移一类，行为用现有六性检查做回归保障。
- 大屏资产目录改为**由 descriptors + dataset cards 生成**，人读界面与机器登记永不脱节。

**M2：元数据外化——Croissant + OpenLineage 的轻量做法（2–3 天）**

- Croissant：为 DWS 层资产各生成一份 Croissant JSON-LD（RecordSet/Field 指向 Parquet 文件），用官方 `mlcroissant` Python 库校验 [[7]](https://mlcommons.org/working-groups/data/croissant/)；同时给资产目录页加 schema.org `Dataset` 结构化标记（Google Dataset Search 的收录前提 [[6]](https://developers.google.com/search/docs/appearance/structured-data/dataset)）——若未来想把公共数据集对外发布，这一步即"可被发现性"。
- OpenLineage：流水线每次运行 emit 一条 run/job/dataset 事件，先落地本地 JSONL（`lineage/events.jsonl`），schema 按 OpenLineage 规范 [[20]](https://github.com/OpenLineage/OpenLineage)；大屏血缘图改读该文件。事件文件同时回流数据中台，成为第 16 类来源。
- 质量门禁升级：六性检查规则改写为 pandera schema（规则即代码、随 git 版本化 [[34]](https://pandera.readthedocs.io/en/stable/)），流水线入口强制执行，失败即阻断回流（借鉴 lakeFS WAP hooks 的"先审计后发布" [[15]](https://docs.lakefs.io/)）。

**M3：版本契约化（跨项目共享出现后启动）**

- 版本三元组：每次评测/实验记录 `(upstream_revision, pipeline_commit, dataset_sha256)`——上游锚点用 HF revision/DOI（[[16]](https://huggingface.co/docs/datasets/en/loading)、[[4]](https://zenodo.org/help/versioning)），中间锚点用 git commit，末端锚点用现有 SHA-256。数据体量增长、需要回滚数据快照时再评估 DVC（[[14]](https://doc.dvc.org/)）或 lakeFS（[[15]](https://docs.lakefs.io/)）。
- 数据集卡升级为简版 ODCS 契约（models/schema + servicelevels + quality 阈值 + terms），遵循当前行业标准而非已弃用的 datacontract.com 规范 [[25]](https://github.com/bitol-io/open-data-contract-standard)、[[24]](https://github.com/datacontract/datacontract-specification)。
- 存储演进：DWD/DWS 层 Parquet 化 + DuckDB 查询 [[36]](https://duckdb.org/why_duckdb)、[[29]](https://parquet.apache.org/docs/)；仅在出现多写者 ACID / 快照时间旅行需求时引入 PyIceberg [[30]](https://iceberg.apache.org/docs/latest/)。
- 评测层解耦：评测用例引用 `dataset_id@revision` 而非硬编码路径，对齐 OpenCompass/lm-eval 的配置-数据-指标三层 [[21]](https://github.com/open-compass/OpenCompass)、[[23]](https://github.com/EleutherAI/lm-evaluation-harness)；对外部基准的评测结论，在卡上记录推理模型训练截止时间以支撑污染时间断面分析 [[13]](https://arxiv.org/html/2406.04244v1)。
- 渠道风险登记：外部基准的"上游渠道"标注存活性（PwC 已关站之鉴 [[39]](https://paperswithcode.com/datasets)），镜像渠道（OpenDataLab/ModelScope/天池）只作下载通道，可信锚点一律回指上游 [[7]](https://mlcommons.org/working-groups/data/croissant/)。
