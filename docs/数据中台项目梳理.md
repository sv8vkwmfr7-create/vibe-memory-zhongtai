## 1. 一句话定位

为 VibeMemory（编码 Agent 的本地图记忆系统）配套建设的**数据中台底座 + 评测/测试/监控三能力中台**：把散落在仓库、本机与服务器上的实验、覆盖率、评测与运行时产物，统一成「有指纹、有血缘、有质量分、可对外取数」的数据资产，再用可复现的门禁回答「这周比上周好没好」。

**边界（先说清楚，避免过度声明）**：单机文件型实现，验证的是方法论与数据流；明确不做分布式存储、多租户权限、实时流处理。

---

## 2. 四中台各回答什么问题

| 中台 | 回答的问题 | 输入 | 输出（回流数据中台） | 门禁 |
| --- | --- | --- | --- | --- |
| **数据中台**（底座） | 有哪些可信数据、质量如何 | 被测仓库产物 + 三个能力中台存档（共 21 类来源） | ODS/DWD/DWS 三层资产、目录、溯源、质量六性 | 质量分 ≥ 0.85 |
| 评测中台 | 记忆**检索质量**好不好 | 30 个评测集 / 5,584 用例 | `runs/run-*.json`（指标 + Wilson CI） | 指标阈值 + 环境可比性 |
| 测试中台 | 改代码**没改坏**吧 | 仓库 `tests/`（pytest + junitxml/coverage） | `runs/test-*.json`（通过率/覆盖率/失败明细） | 绝对门禁优先（任一失败即 FAIL） |
| 监控中台 | 跑起来**快不快、稳不稳** | SDK 确定性混合负载（seed 可复现） | `runs/obs-*.json`（延迟分位/命中率/降级） | 观测层，异常靠对比历史 |

> 关键辨析：**评测 ≠ 测试 ≠ 监控**。评测度量检索质量，测试度量代码回归，监控度量运行时行为；三者存档全部回流数据中台，统一目录、统一溯源、统一呈现。

## 3. 架构：三个位置、一条数据流

```
本机 Windows（RTX 4060 8GB）
  · 每天 10:00 计划任务 daily_runs.py：跑评测/测试/监控 → 产出三件套 → 增量 scp → POST /api/refresh
  · 幂等（当天已有存档跳过）+ 水位同步（.sync_state.json）+ 失败下轮补传
GitHub push ──→ instabox 云服务器（Debian）
                  · autopull：每 15 分钟 git fetch，新提交自动跑流水线
                  · 流水线 server_pipeline.sh：collect → build_assets → quality → signals → pages
                  · zhongtai :8080 大屏 + 12 个数据 API ｜ archive :8081 全档浏览
                  · keepalive：每 10s 自检 + 心跳落盘 + 连续 6 次失联自动重启（自愈）
                  · cloudflared ×2 隧道 → 公网大屏 / 档案 / API
浏览器（5 张静态大屏）· 程序（/api/data/* 取数）
```

四个 systemd 用户服务（`Restart=always` + Linger 自启）：`zhongtai` / `archive` / `autopull` / `keepalive`。

## 4. 数据中台（底座）怎么实现

### 4.1 适配器接入：新项目零核心代码

- 每个项目一份 `数据中台/projects/*.json`：`project_id`、`root`（按 Windows/Linux 给根）、`license`、`sources[]`（id/kind/path/pattern/required/desc）。
- `collect.py` 用 `@extractor` 装饰器注册 **11 种抽取器**：`json_dir / jsonl_dir / jsonl_file / json_file / markdown / markdown_dir / file_dir / coverage_xml / test_dir / git_log / toml_file`。
- 接入新项目 = 写一个 JSON（或注册一个函数），核心代码不动。实证：知识库、codex-zcode-team 两个项目当天接入，3 项目 21 类来源双环境全绿。

### 4.2 三层加工与"数据身份证"

```
ODS 原始层：逐来源快照 + SHA-256 指纹 + 记录数/大小/mtime + 变更检测（不改原始数值）
  → DWD 明细层：清洗/规范化/炸开（实验逐文件、评测逐题 8,742 行、junit 逐用例 5,513 行）
  → DWS 汇总层：面向应用的指标主题（仓库健康/实验指标/评测汇总/周对比）
```

- **版本三元组**：每个资产带 `upstream_revision`（被测仓库 commit）+ `pipeline_commit`（中台代码指纹）+ `dataset_sha256`。
- **血缘**：collect/build_assets 每次运行发 OpenLineage 风格事件（job → inputs → outputs），追加 `assets/lineage_events.jsonl`；`/api/data/lineage` 可查。
- **记账特性（真实口径）**：`records_total` 是全量重建水位，重跑不涨行；增长刻度用 lineage 逐日事件数与 runs 存档数，门户有「近 14 天数据活动」图。

### 4.3 质量与信号

- `quality.py` 六性检查：**完整性 / 唯一性 / 一致性 / 准确性 / 及时性 / 有效性**，每维 0~1 分，综合分为维度均值；阈值 0.85，低于即 signal。
  - 及时性为 90 天满分窗口 + 线性衰减（`1 - (days-90)/365`），避免"越老越沉默"。
- `signals.py` 把运维状态变成可读信号（当前 9 条、6 类）：数据停更（评测/测试/监控 >48h warn、>96h bad）、来源健康（必需来源缺席=bad）、质量门禁、测试门禁、项目新鲜度（文档/事件流 14 天 warn、28 天 bad）、服务心跳（>5min bad）。
- 当前唯一 bad 是 codex 事件流闲置 35 天——**诚实状态，不是故障**。

## 7. 值得讲的工程点（面试主线）

1. **适配器模式**：多项目接入从"改代码"变成"写描述文件"，11 种抽取器覆盖目录/单文件/Markdown/覆盖 XML/git log/TOML。
2. **数据身份证**：指纹 + 版本三元组 + 血缘事件，任何一条资产都能回答"从哪来、哪版代码产的、源文件变过没"。
3. **口径诚实**：发现 `records_total` 是全量重建不涨行后，改用 lineage 逐日事件 + runs 存档数计增长，并把这条写进文档——避免"看着在涨，其实没长"。
4. **双协议评测**：`pooled`（共享实例，模拟真实单 Agent 记忆库互相干扰）与 `isolated`（逐题独立，对齐 LoCoMo/LongMemEval 官方协议）；门禁带**环境可比性告警**（池规模差 3 倍或协议不同即提示"指标不可直接对比"）。
5. **评测/测试/监控解耦**：召回评测秒级进每日管线；答案级 LLM-judge（本地 Qwen3-4B NF4，GPU 约 50 分钟）独立执行器，避免重活拖垮日报。
6. **审计驱动的门禁修正**：原测试门禁只看通过率相对下降，1,359/1,360 也会 PASS；改为**绝对门禁优先**（任一失败即 FAIL），并把失败明细解析的 junit 布尔陷阱（空 Element 判 False）一起修掉。
7. **无人值守 + 自愈**：定时幂等、增量水位、失败补传、服务失联自愈、异常信号面板，整机 8 小时上限/30 分钟睡眠约束下仍能自动恢复。
8. **零依赖前端**：五张大屏静态内嵌、自带 SVG 图表，无 CDN、断网可开（国内网络环境下的工程取舍）。

## 10. 面试追问准备

| 追问 | 回答要点 |
| --- | --- |
| 这和数仓/数据中台有什么区别？ | 同构分层（ODS/DWD/DWS + 质量 + 资产目录 + 统一出口），但去掉了集群组件；重点不是算力，而是"可信可追溯 + 能被程序消费"。对齐信通院《数据中台实践指南》与 OneData 的方法论已在 `docs/数据中台调研.md` 梳理。 |
| 18,699 条怎么算的？ | `catalog.json` 里 16 个资产的 rows 求和：评测逐题 8,742 + junit 逐用例 5,513 + 公开数据集 4,010 为主，ODS 快照 21 行是来源级汇总。 |
| 为什么不上 DataHub/Spark/Flink？ | 单机 + 1 人 + 数据量万级，重组件只会增加常驻故障点；选择零依赖文件型实现，把复杂度留给"口径与门禁"。这是有意的取舍，不是做不了。 |
| 质量六性怎么打分？ | 每维独立规则：完整性=必填字段非空比例，唯一性=主键重复率，一致性=跨资产口径/外键，准确性=取值合法（如覆盖率 ∈[0,1]），及时性=90 天窗口线性衰减，有效性=解析成功率/枚举合法；综合分为六维均值，0.85 为门禁。 |
| 血缘怎么实现？ | collect/build_assets 每次运行发 OpenLineage 风格事件（job、inputs、outputs、时间），追加 jsonl；catalog 每个资产同时带 upstream 与 transforms，API 可查事件流。 |
| 版本三元组为什么需要？ | 只记数据指纹不够——还得知道是哪版代码、哪版被测仓库产出的，否则"指标变了"分不清是数据变了还是代码变了。 |
| 双协议为什么必要？ | pooled 下所有评测集共享一个记忆库（1,508 atoms），语义近邻互相干扰，模拟真实单 Agent；isolated 逐题建库，对齐官方评测。混用会让指标失真，所以门禁检查协议与池规模（差 3 倍即告警）。 |
| 门禁如何避免误报？ | 绝对阈值 + 基线容忍带 0.05 + 环境可比性告警 + `NO_BASELINE` 状态；INT/FAIL 退出码区分（2=无结果，1=失败），CI 可判。 |
| 怎么保证无人值守？ | 定时任务幂等（当天有存档就跳过）、scp 水位增量（失败下轮补传）、systemd Restart=always、keepalive 连续 6 次失联重启、signals 面板把异常变成可读状态。 |
| 数据量增长怎么证明？ | `records_total` 是全量重建水位（重跑不涨），真实增长看 `lineage_events.jsonl` 逐日事件 + `runs/` 存档数；门户「近 14 天数据活动」图即此口径。 |
| 最大的短板？ | 单机文件型、指标单环境、PersonaMem 32.6% / 对抗纠偏 2.2% / 遗忘 27% 都是真短板，已在待办；下一步是固定域名、第 4 个项目接入、监控负载 1000→5000 atoms。 |
