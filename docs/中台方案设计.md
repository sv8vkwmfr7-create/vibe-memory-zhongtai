# VibeMemory 数据中台 + 评测中台 · 方案设计

> 版本：v2.0（四中台整合）｜ 编制日期：2026-11-08 ｜ 适用对象：`Desktop\VibeMemory`（vibe-memory v0.3.0）
> v2 增补：测试中台、监控中台接入，四中台统一门户与数据底座（见 §9）。

---

## 1. 背景与目标

VibeMemory 是一套带关系标签的分片图记忆系统（分层建边 + 边标签过滤 + PPR 图检索 + BM25/向量/时序多策略 RRF 融合）。随着仓库内实验（`experiments/`）、结果存档（`results/`）、测试与覆盖率产物不断累积，出现两类典型问题：

1. **数据散落**：实验结果、覆盖率、项目状态文档、记忆库各自孤立，没有统一的"资产目录"，无法回答"现在有哪些可信数据、质量如何、能不能用"；
2. **评测不成体系**：合成消融、LoCoMo/LongMemEval 试跑散落在 pytest 临时目录里，缺少固定的**评测集资产**、标准化的**评测流程**、可追溯的**运行存档**和**回归门禁**。

本方案在**独立文件夹 `VibeMemory-中台/`** 内构建两个轻量中台，方法论对齐业界：

| 中台 | 对标方法论 | 在本项目的形态 |
| --- | --- | --- |
| 数据中台 | 信通院《数据中台实践指南》、阿里 OneData（OneModel/OneID/OneService）、数据质量维度（完整性/唯一性/一致性/准确性/及时性对应 GB/T 36344-2018 框架，有效性取自 DAMA 六核心维度） | ODS→DWD→DWS 三层数据资产 + 来源校验 + 质量检查 + 资产目录 + 统一出口（JSON 资产直接供可视化页面消费） |
| 评测中台 | OpenCompass 式"评测集/运行/榜单"抽象（其官方流水线为配置→Partitioner→Runner→Summarizer）、LLM 记忆评测基准（LoCoMo/LongMemEval）的能力维度与指标体系、CI 回归门禁 | 内建评测集（JSONL）+ 评测执行器 + 指标计算 + 运行存档 + 榜单 + 门禁 |

设计原则（依据调研结论的"轻量化、场景驱动"）：

- **薄中台**：不引入 Hadoop/Kafka 级重型组件，纯 Python + JSON/SQLite，双击即可运行；
- **可信优先**：每个数据来源登记指纹（SHA-256）、行数、采集时间，可追溯、可复跑；
- **评测即资产**：评测集本身纳入数据资产目录管理（版本、指纹、变更可查）；
- **可视化即出口**：资产与评测结果以静态 HTML 大屏呈现，零依赖（无 CDN），离线可开。

## 3. 数据中台设计（data-platform）

### 3.1 六层架构映射

按业界通用"六层 + 一贯穿"结构落位：

| 业界分层 | 本项目落位 | 说明 |
| --- | --- | --- |
| ① 数据汇聚 | `collect.py` | 从登记的可信来源采集：校验存在性→计算 SHA-256→提取为 ODS JSON 快照，写 provenance |
| ② 存储与计算 | `assets/ods|dwd|dws`（JSON 文件，未来可平滑换 SQLite/DuckDB） | 文件即库：每层一份 JSON，带 schema 注释 |
| ③ 数据开发 | `build_assets.py` | ODS→DWD 清洗规范化（扁平化、字段标准化、单位统一），DWD→DWS 聚合 |
| ④ 数据资产管理 | `catalog.json` + `quality.py` | 资产目录（含血缘 lineage）+ 质量六性检查 + 质量报告 |
| ⑤ 数据服务 | `assets/*.json` + 可选 `serve.py` | OneService 式统一出口：页面只读资产目录定位文件；可选本地 API |
| ⑥ 数据应用 | `pages/data-platform.html` | 数据资产大屏 |
| ★ 全域治理（贯穿） | `sources.json` 登记 + 指纹校验 + provenance | 源头可信、过程可溯、变更可查 |

### 3.2 可信数据来源（sources.json）

只登记**项目内权威产物**，每条来源声明：id、类型、路径、读取方式、期望内容、采集频率。采集时逐项验证：

- 文件存在、非空；
- SHA-256 指纹（与上次采集比对，变化即记录 diff）；
- 大小与最近修改时间；
- 可解析性与行数/记录数。

首轮登记的可信来源（以仓库实际存在为准，采集器对缺席来源显式报 `missing` 而非静默跳过）：

| id | 来源 | 内容 |
| --- | --- | --- |
| `results_experiments` | `results/*.json` | 实验结果存档（MCP 维护冒烟、磁盘 soak、检查点对照等） |
| `coverage_xml` | `coverage.xml` | pytest 覆盖率报告（行/分支覆盖率） |
| `status_md` | `STATUS.md` | 项目状态、能力边界、待验证事项 |
| `changelog_md` | `CHANGELOG.md` | 版本演进 |
| `seed_memory` | `vibe_memory/seed_memory.json` | 出厂种子记忆结构样本 |
| `tests_index` | `tests/` | 测试文件清单（数量、主题分布） |
| `git_activity` | `git log` | 近期提交活动（提交数、时间跨度） |
| `repo_meta` | `pyproject.toml` | 版本、依赖、Python 要求 |

### 3.3 分层模型

- **ODS（原始接入层）**：源文件的结构化快照（`ods/results_index.json`、`ods/coverage.json` …），不改动原始数值，只做"解析+编目"，保留原始指纹；
- **DWD（明细层）**：清洗规范化后的统一记录模型，如实验记录 `{experiment_id, name, date, metric, value, unit, source}`、覆盖记录 `{module, line_rate, branch_rate}`；
- **DWS（汇总层）**：面向应用的指标主题：仓库健康指标（测试规模/覆盖率/提交活跃）、实验指标最新值表、质量评分汇总。

### 3.4 数据质量六性

`quality.py` 对每个 DWD/DWS 资产输出六维评分（0~1）与综合分：

完整性（必填字段非空比例）、唯一性（主键无重复）、一致性（跨资产外键/口径一致）、准确性（数值合法、单位一致）、及时性（资产年龄）、有效性（枚举/范围合法）。低于阈值的维度在大屏标黄/标红。

### 3.5 溯源档案（provenance）

每次采集生成 `provenance.json`：来源 → 指纹 → 采集时间 → 记录数 → 与上次指纹对比结果。任何资产都能回答："数据从哪来、什么时候采的、源文件有没有变过"。

## 4. 评测中台设计（eval-platform）

### 4.1 评测对象与能力维度

评测 VibeMemory 的**记忆召回能力**，对齐 LongMemEval 提出的记忆核心能力与 LoCoMo 的任务分类，裁剪为六个内建评测集（中文为主，贴近真实 Agent 使用场景）：

| 评测集 | 能力维度 | 说明 |
| --- | --- | --- |
| `basic_recall` | 单跳事实召回 | 会话中陈述事实 → 直接提问，考 BM25/向量/图基础召回 |
| `temporal` | 时序推理 | 事实带时间戳，"某时点之前/之后"类提问，考时序检索与过滤 |
| `conflict_update` | 知识更新（修正推翻） | 同一事实先存旧版、后存修正版，考修正边与新版优先 |
| `multi_hop` | 多跳图推理 | A→B→C 因果/关联链，考跨分片图检索（PPR+边标签） |
| `multi_hop_bridge` | 多跳·显式建边对照 | 与 multi_hop 同题，显式建立「因果接续」边 + causal_bridge，验证图链路价值（首轮实证：66.7%→100%） |
| `preference` | 用户偏好记忆 | 偏好类陈述（语言/风格/禁忌），考偏好召回与注入 |
| `abstention` | 拒答（负面用例） | 提问主体相关但属性从未存入，正确行为是低置信/无命中，防"编造式命中"（规则代理判分） |

### 4.2 评测集格式（JSONL，一行一个用例）

```json
{"id":"BR-001","type":"basic_recall","sessions":[{"session_id":"s1","text":"我们把生产环境 API 超时从 30 秒改成了 5 秒。"}],
 "query":"生产环境 API 超时时间现在是多少？","expected_keywords":["5秒"],"expected_memory_ids":["s1"],
 "notes":"单位与数值必须命中"}
```

- `sessions`：注入用会话（store 阶段逐条写入）；
- `query`：召回问题（recall 阶段）；
- `expected_memory_ids`：标准答案所在会话（判"命中"的依据，主指标）；
- `expected_keywords`：命中片段需包含的关键词（辅助判分，双条件更严格时在 notes 声明）；
- 评测集文件纳入数据中台资产管理：入库时计算指纹、记录用例数与类型分布。

### 4.3 指标体系

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| Recall@K | 前 K 条召回中含任一标准会话的用例占比 | 主指标（K=5） |
| MRR | 标准会话首次命中排名倒数的均值 | 排序质量 |
| nDCG@K | 按多标准答案计折损累计增益 | 多答案排序 |
| KeywordHit@K | 前 K 条含全部期望关键词的用例占比 | 内容级正确性 |
| AbstentionPrecision | 拒答集：前 1 条得分低于阈值的用例占比 | 负面控制 |
| 逐类型分项 | 上述指标按 type 分组 | 定位短板能力 |

### 4.4 评测流程（run_eval.py）

```
加载评测集(校验JSONL) → 建临时内存/临时库 VibeMemory 实例
→ store 阶段: 按用例逐会话注入(记录 memory id 映射)
→ recall 阶段: 逐 query 召回 top-K
→ judge: 会话ID匹配 + 关键词匹配(可扩展 LLM 判分)
→ score: 计算 Recall@K / MRR / nDCG / KeywordHit
→ archive: runs/run-<时间戳>-<评测集>.json（含环境、评测集指纹、逐题明细）
→ gate: 与基线阈值/上次运行对比，输出 PASS/FAIL
```

每次运行是一份**可复现实验**：记录 vibe_memory 版本、Python 版本、K 值、评测集 SHA-256、耗时。

### 4.5 回归门禁（gate.py）

- **绝对门禁**：核心指标 ≥ 基线阈值（首轮运行后固化 `baseline.json`）；
- **相对门禁**：与上一次运行对比，指标下降超过容忍带（如 5%）即 FAIL；
- 门禁结果回写数据中台（作为 DWS 指标之一），大屏展示"门禁状态"。

### 4.6 与公开基准的关系

内建评测集是**轻量冒烟/回归层**；论文级结论仍以 LoCoMo、LongMemEval 等公开基准为准（仓库已有适配试跑）。评测中台的架构（评测集/运行/榜单/门禁）设计上可直接挂载外部基准数据集，作为后续扩展。

## 7. 使用方法

```bash
cd "VibeMemory-中台"
PY="C:\Users\ASYS\Desktop\VibeMemory\.venv\Scripts\python.exe"

# ① 评测中台：跑全部评测集（--all 时各评测集共享一个 :memory: 实例，互为干扰项）
"$PY" 评测中台/run_eval.py --all
# 或单跑一个（注意 multi_hop_bridge 依赖 multi_hop 注入的会话，建议随 --all 运行）
"$PY" 评测中台/run_eval.py --evalset 评测中台/evalsets/basic_recall.jsonl

# ② 回归门禁：首轮 --init 固化基线；此后直接对比
"$PY" 评测中台/gate.py --init
"$PY" 评测中台/gate.py

# ③ 数据中台：采集 → 加工 → 质量检查
"$PY" 数据中台/collect.py
"$PY" 数据中台/build_assets.py
"$PY" 数据中台/quality.py

# ④ 重新生成可视化页面
"$PY" scripts/build_pages.py
```

## 8. 边界与诚实声明

- 内建评测集为**项目自建的回归级评测**，规模有限，不替代 LoCoMo/LongMemEval 等公开基准的论文级结论；
- 数据中台当前为单机文件型实现，验证方法论与数据流，不承诺分布式/多用户能力；
- 判分默认为规则判分（会话 ID + 关键词），LLM 判分留有扩展点，未默认启用；
- 首轮基线来自本机实际运行，换环境（检索配置、语料）后应重测基线。

## 9. v2 增补：四中台整合（2026-11-08）

### 9.1 四中台定位与边界

| 中台 | 回答的问题 | 输入 | 输出（回流数据中台） | 门禁 |
| --- | --- | --- | --- | --- |
| 数据中台（底座） | 有哪些可信数据、质量如何 | 仓库产物 + 其他三中台存档（15 类来源） | ODS/DWD/DWS 资产、目录、溯源、质量六性 | 质量分阈值 0.85 |
| 评测中台 | 记忆**质量**如何 | 25 套评测集 / 2,568 用例（双协议） | runs/*.json（含 Wilson CI） | 指标阈值 + 环境可比性 |
| 测试中台 | 代码**回归健康**如何 | 仓库 tests/（pytest，junitxml+coverage 证据化） | runs/test-*.json（通过率/覆盖率/失败明细） | 通过率相对门禁（2pp） |
| 监控中台 | **运行时健康**如何 | SDK 确定性混合负载（唯一锚点语料，seed 可复现） | runs/obs-*.json（延迟分位数/命中率/降级） | 无阈值（观测层），异常靠对比历史 |

边界澄清：**评测≠测试≠监控**——评测度量"检索质量"（对语料的召回正确性），测试度量"代码回归"（pytest 通过率），监控度量"运行时行为"（延迟/命中率/降级事件）。三者数据全部回流数据中台，统一目录、统一溯源、统一呈现。

### 9.3 整合原则

1. **单一数据底座**：任何中台的运行存档都是数据资产，回流统一目录（catalog.json 含 13 资产）；
2. **统一门禁语义**：所有门禁都是"当前值 vs 基线/上一轮 + 环境可比性检查"，FAIL 时给出可解释原因；
3. **统一呈现**：五张静态大屏（门户 + 四中台），统一导航、统一设计语言、零外部依赖；
4. **可复现优先**：测试（pytest 命令）、监控（seed 负载）、评测（seed 评测集）全部确定性可重放。
